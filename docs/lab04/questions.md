# Відповіді на питання захисту — Лабораторна 4

Домен — **Замовлення**. Сутності: `Order` (агрегат) + `OrderLine`, стан `OrderStatus`. Код — `Core/Domain`.

---

**1. Що таке інваріант? Назвіть свої і де кожен перевіряється.**
Інваріант — умова, яка має лишатися істинною протягом усього життя об'єкта. Наші:
- Id замовлення/клієнт не порожні → `Order.Create`;
- Id товару/назва рядка не порожні → `OrderLine.Create`;
- ціна ≥ 0, кількість > 0 → `OrderLine.Create`;
- не додати рядок у підтверджене/скасоване → `Order.AddLine`;
- не підтвердити порожнє → `Order.Confirm`;
- лише допустимі переходи статусів → `Order.RequireTransition`.

**2. Навіщо інкапсуляція, якщо дані все одно з файлу і їх можна підправити руками?**
Дані з файлу — недовірені. Інкапсуляція гарантує, що навіть якщо у файлі сміття, у пам'ять потрапить лише коректний об'єкт: усі значення проходять через `Create`/`FromDto`. Зовнішній код не може випадковим присвоєнням (`_lines`, `Status`) перевести об'єкт у некоректний стан — цих полів ззовні просто не видно.

**3. Чому конструктор приватний, а створення — через статичний метод?**
Щоб була **єдина** точка створення з перевірками. Приватний конструктор лише записує вже перевірені значення; фабрика `Create` спершу перевіряє всі аргументи. Результат завжди один із двох: коректний об'єкт або виняток — напівстворених об'єктів немає. Публічний конструктор дозволив би обійти перевірки.

**4. Коли ArgumentException, а коли InvalidOperationException? Приклад кожного.**
- **ArgumentException / ArgumentOutOfRangeException** — некоректний **вхідний аргумент**, сам по собі: `Order.Create("O-1","  ")` → порожній клієнт; `OrderLine.Create(...,-5,...)` → від'ємна ціна.
- **InvalidOperationException** — аргумент нормальний, але **стан** не дозволяє операцію: `order.AddLine(...)` після `Confirm()` → замовлення підтверджене.

**5. Що таке анемічна модель і чим вона погана для вашого проєкту?**
Анемічна модель — клас із самими `{ get; set; }` без методів і правил. Вона компілюється, але не гарантує коректності: будь-хто виставить `Quantity = -5`. Для нас це погано, бо на тижнях 5/10/12 сервіс, Api і Blazor використовували б цю модель і кожен мусив би перевіряти правила сам — правила розповзлися б і десь загубились. Ми ж тримаємо правила в одному місці — у сутності.

**6. Чому назовні віддається IReadOnlyList, а не List?**
Щоб зовнішній код не міг `Add`/`Clear`/`Remove` в обхід інваріантів. `_lines` приватний, а `Lines => _lines.AsReadOnly()` дає лише читання. Якби повертали сам `List<T>`, з нього можна було б додати рядок без перевірок AddLine (або привести тип назад до List) — і агрегат втратив би контроль.

**7. Ваш DTO і ваша сутність — чим відрізняються за призначенням?**
DTO (`OrderDto`/`ProductDto`) — **дані**: переносити й зберігати, без правил. Сутність (`Order`/`OrderLine`) — **поведінка**: приховує стан і гарантує інваріанти. Схожі поля — нормально, ролі різні. Зв'язок — `ToDto`/`FromDto`.

**8. Чи потрібні перевірки в Cli, якщо вони вже є в домені?**
Ні, дублювати не треба. Cli лише викликає доменні методи й обробляє винятки (`try/catch`). Правила — один раз у домені; це і є сенс переносу логіки в Core.

**9. Що станеться, якщо Cli і Api перевірятимуть правила кожен сам?**
Перевірки почнуть розходитись: десь правило суворіше, десь його забули. З'являться шляхи створити некоректний об'єкт в обхід. Тому правила — у домені, а клієнти лише його викликають.

**10. Чому повідомлення винятку містить конкретні числа й ключ запису?**
Щоб помилку можна було зрозуміти й відтворити без перегляду коду: «Неможливий перехід Confirmed -> Confirmed для замовлення O-001» одразу каже, що і з чим сталося. На тижні 10 Api за типом винятку віддаватиме різні HTTP-коди, а текст піде користувачу.

**11. Який стан у вашій моделі не можна змінити після створення і чому саме він?**
`Id` і `CustomerId` — `{ get; }`, без сетера: це ідентичність замовлення. По `Id` на тижні 5 працюватиме `GetById` у сховищі, тому він має бути стабільним. `Status` змінюється, але лише всередині класу (`private set`) і лише дозволеними переходами.

## Додаткові завдання (готові пояснення)

**Дод. 1 — зв'язок із тижнем 3.**
`OrderAssembler.BuildLines(ImportResult<ProductDto>)` бере результат імпорту й будує доменні рядки `OrderLine`, а ті, що не пройшли доменні інваріанти, збирає в окремий список — та сама ідея «дані + помилки», але вже на рівні домену. Вивід: «Побудовано рядків: 10, відхилено: 3».

**Дод. 2 — інваріант між двома сутностями.**
Приклад: «не видати примірник читачу, у якого вже 5 відкритих видач». Таке правило охоплює кілька об'єктів і потребує підрахунку по сховищу, а сутність бачить лише себе. Тому крос-сутнісні правила виносять у **сервіс** (тиждень 5), а не в сутність. У сутності лишаються правила про її власний стан.

**Дод. 3 — явний стан і переходи.**
`enum OrderStatus { Draft, Confirmed, Cancelled }`. Дозволені переходи перевіряє `RequireTransition` через switch expression: `Draft→Confirmed`, `Draft→Cancelled`, `Confirmed→Cancelled` — дозволені; решта кидає `InvalidOperationException`. Демо: скасоване замовлення (`Cancelled`) не можна підтвердити.
